# AGENTS.md — ui-webview (webview panel + element annotation)

Rules for the ui-webview plugin: the webui's right-side page-preview panel, in-iframe element selection and commenting, and the AI collaboration loop that turns annotations into workspace source edits.

**This plugin lives OUTSIDE the harness checkout** — it is developed in the user's own repo (limao-magic-ui) and loaded into a `dsh web` instance by a launch overlay, with zero modifications to the deepseek-harness source tree. The relevant upstream contracts: [packages/client/AGENTS.md](../../../deepseek-harness/packages/client/AGENTS.md), the [slot system standard](../../../deepseek-harness/.agents/notes/implemented/architecture/2026-07-22-slot-type-chain-implementation.md), and the repo-wide [conventions](../../../deepseek-harness/AGENTS.md#conventions) — read them before touching slots, stores, or inject faces. (Path note: when this file moves into a harness checkout, rewrite the `deepseek-harness`-anchored links as relative paths.)

## Loading model (why the entry name is an absolute path)

- `dsh web` boots `base.cordis.yml` (apps/cli/config) as the root include; the web overlay and the `--config` file are flattened patch lists applied to that one include level. The Loader resolves entry names against `ctx.baseUrl` = the boot config's directory (apps/cli/config), and client-modules (the browser-bundle table) resolves package manifests with `createRequire(ctx.baseUrl)` from the same anchor.
- An external package is therefore reachable ONLY through an **absolute-path entry name**: both the Loader's `internal.import` and `require.resolve(<name>/package.json)` treat absolute paths as self-resolving, independent of baseUrl. Relative names, workspace: deps, and nested includes all fail somewhere in this chain — do not "simplify" the absolute path.
- The entry name points at the package **directory**, and the package root carries a thin `index.ts` re-export (`export * from './lib/index.js'`): Node/tsx ESM has no directory resolution, and the loader's resolver tries `<dir>/index.<ext>` — without the root entry the load fails with `ERR_MODULE_NOT_FOUND` on `index.json`. The directory form is what keeps `require.resolve(<name>/package.json)` (client-modules' manifest scan) working — a file-path entry would break that scan.
- The launch overlay (`cordis.yml`) inserts one row: `- insert: - { id: ui-webview, name: <absolute path to this package> }`. The **tsdown client-bundle banner id must equal the entry name** (`__ModuleLoader__.load({ id: ... })` is checked against the boot-graph row id by `arrive()`); the tsdown config reads it from the generated `packages/ui-webview/entry-name.json` (single source shared with `cordis.yml` via `pnpm gen-config`).
- The built node half must stay **self-contained**: the Loader imports the external package from its own directory, which must not require a local `node_modules`. Small DSH construction helpers (`createUserMessage`, `SessionId`) may be value-imported in source only when tsdown inlines them into `lib/index.js`; a surviving bare runtime import is a load-order regression.
- HMR: the repo's `pnpm run dev:web` watch scans only harness `packages/*/*`; the external bundle is watched by the package's OWN tsdown watch (`pnpm run dev:watch`). `dsh web --dev` host polls the bundle files it serves and broadcasts rebuilt frames regardless of who rewrote them.

## Repository conventions

- **The whole repo is TypeScript** — scripts/, demo/, tests/, and the package root's `index.ts` included. `scripts/*.ts` and `demo/server.ts` run via tsx (`pnpm dev`, `pnpm demo`, `pnpm gen-config`); they are typechecked by the `tsconfig.scripts.json` project in the solution. The one deliberate exemption: `packages/ui-webview/index.ts` (the Loader's directory-import forwarding entry) is NOT part of any tsc program — it references the tsdown output (`lib/index.js`) which has no declarations; its correctness is pinned by the real-loading test in `tests/entry-load.spec.ts` instead.
- **Generated files are gitignored**: `cordis.yml` and `packages/ui-webview/entry-name.json` are produced by `pnpm gen-config` (machine-specific absolute paths — committing them would mislead every other checkout). `lib/`, `dist/`, `*.tsbuildinfo`, `.env*`, `*.log`, `coverage/`, `test-results/`, `playwright-report/`, `.artifacts/` are also ignored. A commit must not add them; `pnpm check` fails if gen-config would change the files.
- **Pre-commit hook** (zero-dependency, `core.hooksPath` → `scripts/git-hooks`, installed by the `prepare` script on `pnpm install`): runs the fast gate — `tsc -b --force`, `vitest run`, and gen-config idempotence. The e2e browser suite is deliberately NOT in the commit gate (it spawns services and needs a provider key); run `pnpm test:e2e` for UI changes.
- **Quality gate**: `pnpm check` (all gates) / `pnpm check --e2e` (plus the browser suite). Gate list: typecheck, unit suite, gen-config idempotence, bundle banner-id == entry-name contract, directory-import entry presence, tsdown build. Pre-commit runs the fast subset.
- The repo is a git repository; commit messages follow the convention of the first commit.

## Scope and ownership

- **One dual-face package.** The node half (`src/index.ts`) hosts the `/webview-proxy` route and the `/webview-annotations` structured context-commit route; the browser half (`src/client/`) is the preview tab UI, picker injection, annotation store, and acknowledged dock sync. The node half is NOT a generic fetch gateway. There is no `agent/prompt-submit` listener and no prompt rewrite.
- **Plugin export shape:** named exports `name` / `inject` / `Config` (when present) / `apply`, no default export — a default export makes the Loader discard the namespace (upstream postmortem 0001).
- **The preview is a `conversation.view` tab** (`id: 'webview'`, label 预览/Preview, order 20, review-panel style) and the annotation strip is a **`conversation.input.dock` entry** (`id: 'webview-annotations'`, order 15, GoalBar style) — both registering the SAME apply-constructed store handle (`store: webviewStore` from `createWebviewStore()`, the ui-conversation chatStore multi-registration pattern: a `StoreHandle` in the `store` seat is shared per scope, a `StoreFactory` would instantiate per entry). The harness shell (ui-layout) is NOT modified: no new slot, no column changes. Both roots carry `data-webview-ui`.
- Cross-plugin panel control goes through the plugin's own store and the `ctx.layout` service only where already offered (`closeDetails`); nothing reaches into another package's store or registers into a slot it did not declare.
- **Product copy is Chinese; code comments, JSDoc, and this file are English** (upstream convention). Locale files contain UI copy only. The locale-independent model context template is pinned in node-owned `annotation-context.ts`, never assembled by components.

## Proxy contract (`/webview-proxy`)

- **Request shape:** `GET /webview-proxy/<path-encoded target>` — the target URL is percent-encoded with `/` kept raw (`encodeTarget`), NOT a query parameter: a query-string base would break relative resolution through the injected `<base>` (relative references replace the base's query). Unparseable or non-http(s) targets → 400. Server-side `fetch` with redirect-follow, ~15s timeout, 10MB response cap. No browser cookies: login-gated pages are the direct mode's job, not the proxy's.
- **HTML responses:** strip `content-security-policy`, `content-security-policy-report-only`, `x-frame-options`; inject `<base href="/webview-proxy/<path-encoded page directory>/">` as the first `<head>` child (this makes every relative URL in the document — including script `fetch('x')` — resolve through the proxy); rewrite absolute AND root-relative http(s) URLs in `href | src | action | srcset | poster | data-src` attributes (single- and double-quoted forms) to proxy URLs (root-relative refs do NOT resolve against `<base>` paths, so they must be rewritten); leave `javascript:` / `mailto:` / `data:` / `tel:` / `blob:` / `file:` / `#` / `?` / plain-relative values untouched. `<form action>` is rewritten for GET and POST; POST forwards the body. `Accept: text/html` navigation to any proxied path fetches the target URL verbatim, so an SPA dev server's fallback serves its index.html through the proxy.
- **Non-HTML responses** (js/css/images) pass through with the target's content-type, no rewriting beyond the CSP/XFO strip.
- **All rewriting lives in pure functions** in `rewrite.ts`: `(html, targetUrl, proxyPrefix) => string` (plus the URL-rewrite helper). The route handler is a thin shell: parse, fetch, branch, stream. No regex-over-HTML anywhere else, no mutable rewrite state, no shared caches.
- **SSRF guard:** only http(s) targets are fetchable; no allowlist-less localhost exemptions without a real consumer need.

## Picker contract (same-origin injection)

- **Same-origin detection:** `try { iframe.contentDocument }` — the iframe is same-origin exactly when it loaded through the proxy. No other signal.
- **Injection:** one `<style>` (hover outline, pick-mode cursor, marker/comment styles) plus one `<script>` evaluated in the iframe document, both authored as template-literal strings in `src/client/picker.ts` — no build-time asset pipeline, no `postMessage`. The script registers `window.__dshWebviewPicker = { activate, deactivate, isActive, onPick, onCancel, onMarkClick, onCommentCommit, onCommentDismiss, commentPlaceholder, syncMarkers, openComment, closeComment }`; the parent drives it with direct cross-frame function references (same-origin). The page DOM is **untrusted data, read-only**: never evaluate page content, never write into the page beyond the picker's own style/script, the marker circles it appends, and the floating comment field.
- **Picker behavior:** hover highlights the deepest element under the pointer; in pick mode a click on an unannotated element hands it to `onPick` (the parent opens a floating comment field next to it); a click on an already-annotated element or its marker hands the pick id to `onMarkClick` (re-open that comment). Clicks never navigate (`preventDefault`) and never mutate the page. The floating field (Enter → `onCommentCommit`, Esc → `onCommentDismiss`) and the numbered marker circles (repositioned on scroll/resize) are panel chrome — `isChrome` exempts them from picking. Esc with no field open or a second toggle deactivates pick mode.
- **cssPath:** delegated to `css-selector-generator` (runtime dependency, inlined into the client bundle) with the priority `['id', 'class', 'tag', 'nthoftype']` — order is priority, output is the shortest unique selector, so index segments appear only when uniqueness requires them; `null` falls back to the bare tag. The picker script itself is event-only and never embeds DOM-traversal logic.
- **Snapshot fields** (exact keys, mapped to the wire shape by `annotation-snapshot.ts`): `tagName`, `id`, `className`, `cssPath` (shortest unique selector — runtime anchor for marker rebuilds), `fullPath` (complete ancestor chain), `label` (accessible label), `role` (explicit/implicit ARIA role), `stableClasses` (semantic classes; utility/hashed/variant tokens filtered), `anchor` (framework source anchor or null), `outerHTML` (≤1500 chars), `textContent` (≤300 chars), `rect`, computed `display/position/font-size/color/background-color/margin/padding/width/height`. Caps are contract — enforce at capture and at the node wire boundary, and test exact limits. The source anchor comes from `source-anchor.ts`: framework-agnostic probing of React fiber `_debugSource`, Vue `__file`, and Svelte `__svelte_meta` (defensive reads, null in production builds/unknown frameworks).
- **The page always loads through the proxy** — there is no direct/cross-origin mode, so element picking is always available (login-gated pages simply cannot be annotated; see Known limitations).

## Annotation message and AI collaboration

- **Structured wire, node-owned text.** The browser POSTs `{ sessionId, page, comments[] }`, never XML/Markdown. `annotation-contract.ts` pins request/count/field/context caps; `annotation-context.ts` strictly validates and is the single assembly point. Malformed, oversized, wrong-content-type, and unknown-session requests fail visibly.
- **Stable Browser Comments format.** The context is English regardless of UI locale and starts with `# Browser comments`. Each full snapshot says it supersedes earlier snapshots. Page/target metadata is explicitly untrusted page evidence; only `Comment (user-authored)` is user input. It includes URL/title, role/tag + accessible label, selector, full DOM path, and either source/component or stable classes. Every comment line is block-quoted. Empty comments omit the Comment field. Raw outerHTML, styles, rectangles, and screenshots are excluded.
- **Separate context path.** The node face resolves the live branded `SessionId`, creates a user-role message with `{ kind: 'plugin', plugin: 'ui-webview' }`, and calls `agent.inject`. This is logged and reconstructed as the native 「上下文注入」/Context injection row. It does not wake the model. Identical snapshots are deduplicated per live session; clearing after an active snapshot injects an explicit empty snapshot; initial empty state is a no-op; `agent/disposed` releases dedupe state.
- **Stock composer remains authoritative.** The plugin has no send button, never calls `conversation.send`, never listens to `agent/prompt-submit`, and never rewrites or flattens prompt content blocks. Client commits are immediate, serialized, and acknowledged; failures stay visible and retryable. The browser input service has no generic public pre-submit transaction, so a user can still click Send while a commit says syncing. The synced check is the readiness boundary; do not hide this limitation with timers.
- **No model-facing tool is added:** the context is a logged user-role plugin message; the model acts with existing workspace tools (`tool-fs`, bash). Adding a tool requires a consumer that proves the message form insufficient.
- The AI's workspace is the session's workspace root — the dev instance is launched with `cwd` = the user's project directory (or the GUI workspace picker), so `tool-fs` edits land in the project the iframe previews.

## UI discipline

- Follow the four props shares, the store-factory rule, and the data-access ladder (upstream client rules): business state (url, picks, comments, pick mode, panel open/width/split) lives in `createWebviewStore()` declared at register. Components receive everything through props — no ctx, no React contexts, no hand-made hooks.
- **Link interceptor:** a document capture-phase click listener, active **only while the panel is open**. Intercepts only unmodified left-clicks on `a[href^=http(s)://]`; modifier/middle clicks keep default behavior; clicks inside `[data-webview-ui]` (the panel's own chrome) and inside the iframe (events never bubble to the parent document, but the guard is cheap) are never intercepted. Panel closed → listener inert.
- The preview tab chrome is the URL row (input + refresh + external-open + the icon-only **选择元素** pick toggle at the far right), the pick-mode hint strip, and the error strip. The composer dock renders ONE compact capsule (count + sync state + clear), not one chip per pick. Hover or focus opens a light detail card above it; each row shows number, role/tag badge, target label, comment, and source/selector. Row click writes `focusPickId`; the preview consumes it one-shot and re-opens the element. Host chrome uses CSS Modules and DSH tokens/primitives; only iframe-owned picker chrome remains a template-literal style/script.
- Live element references for the echo markers live in a component ref map (`pickRefs`), never in the store (page DOM is untrusted and non-serializable); markers are re-anchored by cssPath after every iframe navigation.

## Known limitations (do not "fix" into breakage)

- **The proxied iframe is not a security boundary.** Arbitrary proxied scripts execute same-origin with the host because the picker uses direct cross-frame references. Structured route validation protects the model-text boundary, not host routes. Complete isolation requires a dedicated proxy origin plus a validated `postMessage` bridge; until then preview only trusted development pages.
- **Annotation commit and stock-composer Send are not atomic.** The public browser input service has no general pre-submit hook. The capsule exposes syncing/synced/error; users must wait for synced. Reintroducing a waterfall or hiding the race behind a delay is not an acceptable fix.
- **Absolute URLs hardcoded in page JS** (e.g. `fetch('http://host/api')`, `new WebSocket(...)`) are not rewritten; root-relative (`/api`) and relative calls work through `<base>`. Fixing this by executing/rewriting page JS, or by adding a headless browser, is a product decision with real consumer demand — not a bug fix.
- **Dev-server HMR websockets** do not survive the proxy; the page renders but live-reload is absent.
- **Server-side fetch carries no browser cookies** — login-gated pages cannot be annotated (element picking requires the same-origin proxy; there is no direct-mode fallback anymore).
- **The absolute-path entry name is machine-specific**: the yaml and the tsdown banner id must both name this checkout's path. Moving the repo requires regenerating both (`pnpm run gen-config`).
- These are documented for users in the package README (Known Limitations section) and in panel hints; changing them needs a consumer-driven design.

## Testing

- **Pure-function suites** for `rewrite.ts` (attribute forms, base injection, non-HTML pass-through, exact caps) and picker helpers (cssPath, snapshot truncation) — node env for the node half; `// @vitest-environment jsdom` pragma for browser halves.
- **One REAL-composition test for the node half** (upstream rule, docs/testing.md): boot a test-only `cordis.yml` through the Loader with the webserver and this package, serve a fixture page from a local http server, and assert the proxy route returns the rewritten HTML.
- **A real-loading test for the external entry** (`tests/entry-load.spec.ts`): imports the package directory in a tsx subprocess (the Loader's own resolution environment) and asserts the exported plugin shape — this is what pins the `index.ts` forwarding entry, since it is exempt from typechecking.
- **Component specs** for the panel (real store engine, stubbed inject/locale) asserting navigation, picker focus handoff, structured snapshots, acknowledgement/error/retry/clear states, hover/focus/Escape detail behavior, and per-item removal.
- **Browser e2e** (`pnpm test:e2e`, Playwright Chromium against spawned services): panel open → proxied iframe renders → annotation flow → capsule/detail/marker echo → host acknowledgement → **full send loop: a separate plugin Context injection precedes the unchanged stock-composer user message** → clearing context acknowledgement. No fixed sleeps may stand in for the acknowledgement boundary. Keyless-by-design via the **configuration layer** (mirroring the harness scaffold): isolated `$DSH_HOME` with a pre-written welcome-notice acknowledgement (`settings.yaml`, exact version match), the provider key resolved through the product's own chain (repo `.env`, then `~/.dsh/.env` — without it a dead-loopback `DEEPSEEK_BASE_URL` makes the probe message fail instantly), the shipped `directory-picker-auto` row replaced by `-browse` (the auto chooser cannot resolve interactions headless), and `llm-deepseek` patched with `retryPolicy.maxRetries: 0` so turns settle without churn. Each scenario connects its own workspace directory so sessions never interfere.
- **`pnpm check`** is the repo gate (typecheck, unit suite, gen-config idempotence, bundle banner-id contract, build); `pnpm check --e2e` adds the browser suite. The harness's own suites (`test:gui`/`test:web`) are not run from this repo — the harness tree is untouched by design.
- Store-factory and component tests call `createWebviewStore().create()` directly — the sanctioned zero-machinery path; production code never calls the factory outside `apply`.

## Local development and verification

- One-time setup: `pnpm install` in this repo (devDeps only — tsdown, react, types, plus `file:`/`link:` type links into the harness checkout), and once in the harness checkout (`pnpm install && pnpm build`) — the latter is the runtime base for `dsh web`.
- **Dev loop:** `pnpm dev` runs `dsh web --dev --port 3090 --config ./cordis.yml` AND this package's tsdown watch together — both must run from the same places per the loading model above; neither alone updates the GUI. Browser refresh applies rebuilt client bundles; node-half changes require restarting the web process (cordis HMR is disabled for web). `pnpm demo` serves the demo page (default port 5173).
- **Verification ladder:** `pnpm check` (typecheck + unit + config/bundle contracts + build) → `pnpm test:e2e` (browser suite; also `pnpm check --e2e`) → manual acceptance. The pre-commit hook runs the fast subset automatically.
- The running 3080 GUI is served from the harness snapshot checkout and is NOT touched by this plugin's dev loop.
- End-to-end acceptance: open a page through the proxy → pick elements → comment → send → model edits workspace source → manual iframe refresh shows the change.
